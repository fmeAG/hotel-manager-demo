## 1. Überblick

Diese Analyse untersucht die Hotel-Management-Anwendung mit Fokus auf die Hotel-Kernfunktionen (Raum- und Gästemanagement, Check-in/Check-out) sowie die neu eingeführte Chatfunktion (Messaging zwischen Rezeption und Gästen).

## 2. Vorhandene Funktionen

### 2.1 Raum-Management

**Status:** BELEGT  
**Quelle:** `docs/overview.md` (Zeilen 13-16), `docs/api.md` (Zeilen 9-47), `app/models.py` (Zeilen 14-23), `app/services/room_service.py`

**Funktionalität:**
- Liste aller Räume abrufen
- Einzelnen Raum abrufen
- Raumstatus ändern

**Raumstatus:**
- `available` — Raum ist frei und kann eingecheckt werden
- `occupied` — Raum ist belegt
- `cleaning` — Raum wird gereinigt

**Geschäftsregel Statuswechsel:** BELEGT  
**Quelle:** `docs/decisions.md` (Decision 009), `app/services/room_service.py` (Zeilen 20-24)
- Ein belegter Raum (`occupied`) kann nur zu `cleaning` gewechselt werden
- Ein direkter Wechsel von `occupied` zu `available` ist blockiert
- Check-out setzt Raum automatisch auf `cleaning`
- Nur ein manueller Wechsel von `cleaning` zu `available` ermöglicht erneute Check-ins

### 2.2 Gäste-Management

**Status:** BELEGT  
**Quelle:** `docs/overview.md` (Zeilen 13-16), `docs/api.md` (Zeilen 50-108), `app/models.py` (Zeilen 25-36), `app/services/guest_service.py`

**Funktionalität:**
- Gäste anlegen (Vorname, Nachname)
- Liste aller Gäste abrufen
- Einzelnen Gast abrufen
- Gast bearbeiten (Vorname, Nachname)
- Gast löschen

**Geschäftsregel Löschen:** BELEGT  
**Quelle:** `app/services/guest_service.py` (Zeilen 26-33), `docs/api.md` (Zeilen 106-108)
- Ein Gast mit aktiver Zimmerzuweisung (`room_id != null`) kann nicht gelöscht werden
- Rückgabewert: HTTP 409 Conflict

**Zeichensatz-Behandlung:** BELEGT  
**Quelle:** `docs/decisions.md` (Decision 007), `docs/changelog.md` (Version 1.3.1)
- Seit Version 1.3.1 werden Umlaute und Sonderzeichen (ä, ö, ü, ß) korrekt gespeichert
- Vor Version 1.3.1 wurden sie stillschweigend entfernt (ASCII-Sanitierung)
- Keine Datenmigration für Altdaten erfolgt

### 2.3 Check-in / Check-out

**Status:** BELEGT  
**Quelle:** `docs/overview.md` (Zeilen 20-30), `docs/api.md` (Zeilen 111-137), `app/services/checkinout_service.py`

**Check-in-Funktionalität:**
- Weist einem Gast einen verfügbaren Raum zu
- Setzt Raum-Status auf `occupied`
- Speichert Check-in-Datum beim Gast

**Geschäftsregeln Check-in:** BELEGT  
**Quelle:** `app/services/checkinout_service.py` (Zeilen 8-22), `docs/api.md` (Zeilen 124-127)
- Gast darf noch keinen Raum haben (`room_id` muss `null` sein)
- Raum muss `available` sein
- Bei Verletzung: HTTP 409 Conflict

**Check-out-Funktionalität:**
- Entfernt Zimmerzuweisung vom Gast
- Setzt Raum-Status auf `cleaning`
- Speichert Check-out-Datum beim Gast

**Geschäftsregeln Check-out:** BELEGT  
**Quelle:** `app/services/checkinout_service.py` (Zeilen 25-34), `docs/api.md` (Zeilen 132-137), `tests/test_checkout_service.py` (Zeilen 40-45)
- Gast muss einen Raum haben (`room_id != null`)
- Raum wird auf `cleaning` gesetzt (nicht direkt `available`)
- Bei Verletzung: HTTP 409 Conflict
- Vorhandener Unittest bestätigt `cleaning`-Status nach Check-out

### 2.4 Messaging-Funktion (Rezeption)

**Status:** BELEGT  
**Quelle:** `docs/decisions.md` (Decision 006), `docs/changelog.md` (Version 1.3.0), `app/models.py` (Zeilen 38-54), `app/api/messages.py`, `static/messages.html`

**Funktionalität:**
- Nachricht an einen Raum senden (Absender, Inhalt)
- Alle Nachrichten auflisten
- Nachrichten nach Raum filtern (`?room_id=`)
- Einzelne Nachricht abrufen
- Nachrichtenstatus ändern

**Nachrichtenmodell:** BELEGT  
**Quelle:** `app/models.py` (Zeilen 44-54), `docs/architecture.md` (Zeilen 78-82)
- `id` — Primärschlüssel
- `sender` — Freitext-String (kein Enum)
- `room_id` — Fremdschlüssel zu `rooms.id` (required)
- `content` — Nachrichtentext
- `created_at` — Serverseitiger Zeitstempel (UTC)
- `status` — Enum: `sent`, `delivered`, `read` (Default: `sent`)

**Nachrichtenstatus-Übergänge:** BELEGT  
**Quelle:** `app/services/message_service.py` (Zeilen 7-11, 32-39), `docs/api.md` (Zeilen 202-205), `docs/decisions.md` (Decision 006)
- Erlaubt: `sent → delivered → read`
- Nicht erlaubt: Rückwärts-Wechsel, Überspringen von Zuständen
- Bei Verletzung: HTTP 409 Conflict
- Explizite Zustandsübergangstabelle in `message_service.py` vorhanden

**Bekannte Einschränkung Sender-Feld:** BELEGT  
**Quelle:** `docs/decisions.md` (Decision 006, Absatz „Consequences")
- `sender` ist reiner Freitext ohne Authentifizierung
- Keine Verhinderung von Impersonation
- Als bekannte Limitation des Trainingsprojekts akzeptiert

### 2.5 Messaging-Funktion (Gast)

**Status:** BELEGT  
**Quelle:** `docs/decisions.md` (Decision 008), `docs/changelog.md` (Version 1.4.0), `static/guest_messages.html`, `static/js/guest_messages.js`

**Funktionalität:**
- Gastsicht über `/guest_messages.html?room_id={id}`
- Gast kann Nachrichten des eigenen Raums lesen
- Gast kann Nachrichten senden
- Automatische Status-Transition `sent → delivered` beim Laden nicht-gast-seitig gesendeter Nachrichten
- Manuelles Setzen von `read` über Button

**Gast-Identifizierung:** BELEGT  
**Quelle:** `docs/decisions.md` (Decision 008, Absatz „Decision")
- Keine Authentifizierung
- Raum-ID als URL-Parameter (`?room_id=`)
- Jeder mit URL kann Raum-Nachrichten einsehen und senden
- Als bewusste Design-Entscheidung dokumentiert (konsistent mit No-Auth-Scope des Projekts)

**Sender-Kennzeichnung Gast:** BELEGT  
**Quelle:** `static/js/guest_messages.js` (Zeilen 1, 8-9, 104), `docs/decisions.md` (Decision 008)
- Gast-Nachrichten setzen `sender` auf festen String: `"Guest (Room {number})"`
- Nicht editierbar durch Gast
- Identifikation von Gast-Nachrichten über String-Präfix-Check: `sender.startsWith("Guest (")`

**Auto-Delivery-Mechanismus:** BELEGT  
**Quelle:** `static/js/guest_messages.js` (Zeilen 43-53, 64-71)
- Beim Laden der Gastsicht: alle Nachrichten mit Status `sent`, die NICHT vom Gast stammen, werden automatisch auf `delivered` gesetzt
- `read` bleibt explizite Aktion (Button)
- Unterscheidung Gast/Rezeption über Sender-String-Präfix

## 4. Offene fachliche Fragen

### 4.1 Raum-Verwaltung

**OFFEN: Mehrfach-Belegung**  
Es ist unklar, ob ein Raum jemals mehr als einen Gast gleichzeitig haben kann.  
**Hinweis:** Schema erlaubt mehrere Gäste pro Raum (`Guest.room_id` FK ohne UNIQUE-Constraint), aber Business-Logik erzwingt „höchstens ein aktuell eingecheckter Gast" laut `docs/architecture.md` (Zeile 87).  
**Frage:** Wird dies auf DB- oder Service-Ebene geprüft? Wie verhält sich Check-in, wenn bereits ein anderer Gast im Raum ist?

**OFFEN: Raum-Kategorie**  
Kategorien (Single, Double, Suite) sind nirgendwo formal definiert.  
**Quelle:** `docs/overview.md` erwähnt sie, aber keine Enum-Validierung in `app/models.py` (Zeile 19: `category = Column(String)`).  
**Frage:** Sind beliebige Strings erlaubt? Gibt es eine Masterliste?

**OFFEN: Cleaning-Workflow**  
Dokumentation beschreibt Übergang `cleaning → available`, aber nicht, wer/wann/wie das geschieht.  
**Frage:** Gibt es eine Anforderung, dass Housekeeping-Personal die Freigabe macht? Oder kann Rezeption willkürlich auf `available` setzen?

### 4.2 Gäste-Verwaltung

**OFFEN: Validierung Gastnamen**  
Seit Decision 007 werden Umlaute akzeptiert, aber es gibt keine dokumentierte Längen- oder Format-Beschränkung.  
**Quelle:** `app/services/guest_service.py` (Zeilen 17-23) — keine Validierung außer DB-Constraint `nullable=False`.  
**Frage:** Sind Leerzeichen erlaubt? Nur Buchstaben? Max. Länge?

**OFFEN: Gast ohne Raum löschen**  
API erlaubt Löschen von Gästen ohne Raum (`room_id == null`).  
**Frage:** Ist das fachlich korrekt? Was passiert mit historischen Check-in/out-Daten? (Aktuell werden sie mit dem Gast gelöscht, da keine Audit-Tabelle existiert.)

### 4.3 Check-in / Check-out

**OFFEN: Zeitpunkt Check-in-Datum**  
Check-in speichert `date.today()` (Python-seitiges Datum).  
**Frage:** Ist das die Server-Zeitzone? Wie wird mit Zeitzonen umgegangen? (Aktuell: keine Zeitzone dokumentiert.)

**OFFEN: Check-out ohne Check-in**  
Ein Gast ohne `room_id` kann nicht ausgecheckt werden (HTTP 409).  
**Frage:** Was passiert, wenn ein Gast manuell via DB oder API `room_id = null` gesetzt bekommt? Bleibt `check_in_date` erhalten?

**OFFEN: Mehrfach-Check-in**  
Ein Gast mit bestehendem `room_id` wird beim Check-in abgewiesen (HTTP 409).  
**Frage:** Ist ein Check-out immer erforderlich, oder gibt es Szenarien (Zimmerwechsel), wo direkt neu eingecheckt werden soll?

### 4.4 Messaging

**OFFEN: Nachricht an nicht-existenten Raum**  
Service prüft, ob `room_id` existiert (HTTP 404 bei ungültig).  
**Frage:** Darf eine Nachricht an einen Raum ohne aktiven Gast gesendet werden? (Aktuell: Ja, nur Raum-Existenz wird geprüft.)

**OFFEN: Nachrichtenlöschung**  
Spec schließt Löschen explizit aus (`specs/chat_feature_spec.md`, Zeile 181), aber keine API-Dokumentation zu GDPR/Datenbereinigung.  
**Frage:** Wie werden Nachrichten archiviert/entfernt? Unbegrenzte Speicherung?

**OFFEN: Zeitstempel-Zeitzone**  
`Message.created_at` nutzt `datetime.utcnow()` (UTC).  
**Quelle:** `app/models.py` (Zeile 51).  
**Frage:** Wie zeigt Frontend diese Zeit? Conversion zu Lokalzeit? (Frontend zeigt `new Date(m.created_at).toLocaleString()` — browserbasiert.)

**OFFEN: Sender-Feld Rezeption**  
Rezeption gibt Sender-String selbst ein (`static/messages.html`, Zeile 31: Defaultwert „Reception").  
**Quelle:** `static/messages.html`, `docs/decisions.md` (Decision 006).  
**Frage:** Ist „Reception" ein fest vorgegebener Wert? Darf der Mitarbeiter seinen Namen eingeben? (Aktuell: Freitext, keine Validierung.)

**OFFEN: Status-Rücksetzen**  
Statusübergänge nur vorwärts erlaubt.  
**Frage:** Was passiert bei versehentlichem „Delivered" markieren, wenn Gast Nachricht noch nicht erhalten hat? Gibt es einen Korrektur-Prozess?

**OFFEN: Gastsicht ohne Raum**  
`/guest_messages.html` ohne `?room_id=` zeigt Raum-Auswahl.  
**Quelle:** `static/guest_messages.html` (Zeilen 28-37).  
**Frage:** Ist das fachlich korrekt? Soll ein Gast alle Räume sehen können? (Aktuell: Ja, keine Einschränkung.)

**OFFEN: Auto-Delivered Logik**  
Gastsicht setzt automatisch `sent → delivered` für Rezeptionsnachrichten.  
**Quelle:** `static/js/guest_messages.js` (Zeilen 43-53).  
**Frage:** Ist das die fachlich korrekte Definition von „delivered"? Oder sollte „delivered" bedeuten, dass die Nachricht mindestens einmal angezeigt wurde (vs. nur API-Aufruf)?

## 5. Erkennbare Produktrisiken

### 5.1 Sicherheit

**RISIKO: Keine Authentifizierung / Autorisierung**  
**Schweregrad:** HOCH  
**Status:** BELEGT als bekannte Limitation  
**Quelle:** `docs/overview.md` (Zeilen 34-38), `docs/architecture.md` (Zeilen 106-110), `specs/basis_spec.md` (Zeile 34), `docs/decisions.md` (Decision 008, Zeile 122)

**Beschreibung:**
- Alle API-Endpunkte sind ohne Credentials erreichbar
- Jeder mit Kenntnis einer Raum-ID kann Nachrichten lesen und senden
- Kein Schutz gegen Cross-Site-Scripting (XSS) bei Nachrichteninhalten (kein HTML-Escaping dokumentiert)
- Kein Schutz gegen SQL-Injection (SQLAlchemy ORM sollte schützen, aber nicht explizit getestet)

**Implikation für Testing:**
- Penetrationstests nicht sinnvoll, da „No Auth" = Scope-Grenze
- Aber: XSS- und Injection-Szenarien sollten geprüft werden

**RISIKO: Sender-Impersonation**  
**Schweregrad:** MITTEL  
**Status:** BELEGT als bekannte Limitation  
**Quelle:** `docs/decisions.md` (Decision 006, „sender field being free text means nothing prevents impersonation")

**Beschreibung:**
- Jeder kann beliebigen Sender-String setzen
- Gast könnte sich als „Reception" ausgeben (Client-seitige Beschränkung ist umgehbar)

**Implikation für Testing:**
- Prüfen, ob API falschen Sender ablehnt (Annahme: Nein)
- Prüfen, ob Frontend String-Präfix-Check umgangen werden kann (Annahme: Ja)

### 5.2 Datenintegrität

**RISIKO: Status-Inkonsistenz bei Check-out**  
**Schweregrad:** MITTEL  
**Status:** TEILWEISE BELEGT durch Test  
**Quelle:** `tests/test_checkout_service.py` (Zeilen 40-45), `docs/decisions.md` (Decision 009)

**Beschreibung:**
- Check-out setzt Raum auf `cleaning`, aber nur ein Test prüft das
- Keine Integrationstests für API-Endpunkt `/api/guests/{id}/checkout`
- Risiko: API-Layer könnte Status-Änderung nicht korrekt umsetzen, auch wenn Service-Layer korrekt ist

**Implikation für Testing:**
- End-to-End-Tests über API erforderlich
- Prüfen: Raum nach Check-out nicht mehr für Check-in verfügbar

**RISIKO: Mehrfach-Check-in bei Race Conditions**  
**Schweregrad:** MITTEL  
**Status:** ANNAHME  
**Quelle:** `app/services/checkinout_service.py` (Zeilen 8-22)

**Beschreibung:**
- Check-in prüft `room.status == available`
- Keine explizite Datenbank-Transaktion mit Lock dokumentiert
- Bei gleichzeitigen Check-ins könnte derselbe Raum zweimal vergeben werden

**Implikation für Testing:**
- Concurrency-Tests erforderlich (parallel Check-ins auf selben Raum)
- Prüfen, ob SQLAlchemy-Standard-Isolationslevel ausreichend ist

**RISIKO: Nachrichten-Status-Race bei Auto-Delivered**  
**Schweregrad:** NIEDRIG  
**Status:** ANNAHME  
**Quelle:** `static/js/guest_messages.js` (Zeilen 43-53, 64-71)

**Beschreibung:**
- Gastsicht führt Auto-Delivered in Schleife aus (ein PATCH pro Nachricht)
- Bei vielen Nachrichten: viele API-Aufrufe
- Bei parallelen Gastsicht-Aufrufen: möglicherweise doppelte PATCH-Aufrufe
- Status-Übergangs-Logik verhindert Fehler (da `sent → delivered` idempotent für bereits `delivered`), aber Performance-Risiko

**Implikation für Testing:**
- Prüfen: Verhalten bei vielen Nachrichten (z. B. 100+)
- Prüfen: Parallele Gastsicht-Aufrufe auf selben Raum

### 5.3 Usability

**RISIKO: Kein Feedback bei Netzwerk-Fehlern**  
**Schweregrad:** MITTEL  
**Status:** ANNAHME (Code-Review erforderlich)  
**Quelle:** Stichprobe `static/js/messages.js`, `static/js/guest_messages.js`

**Beschreibung:**

**Implikation für Testing:**

**RISIKO: Auto-Delivered ohne Sichtbarkeits-Check**  
**Schweregrad:** NIEDRIG  
**Status:** BELEGT als Design-Entscheidung  
**Quelle:** `static/js/guest_messages.js` (Zeilen 43-53)

**Beschreibung:**
- Status `delivered` wird gesetzt, sobald Gastsicht API aufruft
- Keine Prüfung, ob Nachricht tatsächlich im sichtbaren Viewport angezeigt wurde
- Fachlich möglicherweise inkorrekt (wenn „delivered" = „Gast hat es gesehen" gemeint ist)

**Implikation für Testing:**
- Abstimmung mit Fachbereich: Definition „delivered" klären
- Falls inkorrekt: Bug-Report / Änderungsanforderung

### 5.4 Performance

**Implikation für Testing:**

**RISIKO: Unbegrenzte Nachrichten-Historie**

**Status:** OFFEN

- Bei jahrelanger Nutzung: potenziell tausende Nachrichten pro Raum

**Implikation für Testing:**
- Lasttests mit großen Nachrichtenmengen
- Prüfen: Verhalten bei mehreren tausend Nachrichten

## 6. Widersprüche zwischen Spezifikation, Dokumentation und Implementierung

### 6.2 WIDERSPRUCH: Scope Boundaries Messaging

**Quelle:** `docs/overview.md` (Zeilen 32-38), `docs/changelog.md` (Version 1.3.0)
